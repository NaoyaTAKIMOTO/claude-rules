## 2026-11-23 マージの方式をマージコミットに決めた

- ユーザーと話して「リベース ＋ マージコミット」(semi-linear)に決めた
  - 理由: リベースの利点(最新の dev の上でテストする、衝突を feat で直す、履歴がほぼ一直線)をすべて活かせ、PR の区切りとテストファーストの順番も履歴に残る
  - squash も候補だった。1機能が1コミットになるが、リベースによる履歴の利点が消えるので選ばなかった
  - dev → main と main → dev もマージコミットにする。squash すると main と dev の履歴が分かれ、次の PR で同じ差分や衝突が出続けるため
- 整備の項目に、dev のブランチ保護で「最新の dev を取り込むまでマージできない」設定を足した。Require linear history をオンにするとマージコミットが使えなくなるので、使わないと明記した
- 先に必須語(マージコミット squash "linear history")を足して失敗を確かめた。失敗したときの出力:

```
FAIL: check.sh CLAUDE.md
NG: 必須語「マージコミット」がない
NG: 必須語「squash」がない
NG: 必須語「linear history」がない
```

- 本文を直したあと、run-tests.sh はすべて PASS になった

## 2026-11-26 mq の待機が2時間で切れて止まる問題

- 症状: バックグラウンドのコマンドは最長2時間でハーネスに止められる。mq wait <id> を時間の指定なしで待つと、2時間を超えるジョブでは待機ごと止められ、Claude がそこで作業を終えてしまう
- 対策: mq wait の --timeout(時間切れは終了コード 124、ジョブは止めない)を使い、ハーネスの上限より少し短い 7000 秒で待つ。124 で戻ったら失敗とせず、同じ id で待ち直すとルールに書いた
  - ジョブ自身が 124 で終わった場合は、mq wait がジョブの出力を出して返る。時間切れのときは stderr に「still ... after」と出るので見分けられる
- 本文は90行の上限ちょうどだったので、検査は緩めず、88行目を1行のまま書き換えた
- 先に必須語("--timeout 7000" 待ち直す)を足して失敗を確かめた。失敗したときの出力:

```
FAIL: check.sh CLAUDE.md
NG: 必須語「--timeout 7000」がない
NG: 必須語「待ち直す」がない
```

- 本文を直したあと、run-tests.sh はすべて PASS になった
- 実機で確かめた: 順番待ちのジョブに mq wait --timeout 2 をかけると「mq wait: job 162 still Stashed after 2s」で 124 が返り、もう一度待ってもジョブはキューに残っていた。完了後に待ち直すとすぐ結果が返ることは、cmd_wait が時間切れより先に完了を調べるコードで確かめた(試験のジョブは他のスレッドの順番待ちで進まなかったので取り消した)
