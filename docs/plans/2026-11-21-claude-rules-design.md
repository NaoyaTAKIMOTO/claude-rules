# Claude Code 共通ルール 設計メモ(短縮版)

作成日: 2026-11-21

## 目的
- 大目的: 毎回同じ指示を繰り返す手間をなくす
- 中目的: ローカルでもクラウドでも、Claude Code のセッション開始時から同じ作業ルールが効いている
- 小目的: いただいた14項目をルール本文にし、ローカルとクラウドの2か所に置く

## ゴール / 非ゴール / アンチゴール
- ゴール: 新しいセッションで指示しなくても、14項目に沿って動く
- 非ゴール: フックなどでの強制(書いても守られない項目が出てから考える)、既存リポジトリへの一括適用、プラグイン化(案2は将来の選択肢)
- アンチゴール:
  - ルールが長すぎて守られない
  - 簡単な質問への回答にまで重い手順をかけて邪魔になる
  - superpowers と食い違う指示を書く

## 制約(根拠つき)
- クラウドのセッションは、ローカルの `~/.claude/CLAUDE.md` も `settings.json` も読み込まない。公式の方法は、セットアップスクリプトで `~/.claude/CLAUDE.md` を書き出すこと(code.claude.com/docs/en/memory, settings)
- セットアップスクリプトは100行以内、1行200バイト以内。日本語は1文字3バイトなので、1行あたり約60字以内・本文は約90行以内に収める
- ルール同士、またはルールとプラグインが食い違ったとき、どちらが優先されるかは保証されない(公式ドキュメント)。なので食い違いを作らない
- ブランチ保護(e2e が通らないとマージできない設定)は、無料プランの非公開リポジトリでは効かない(私の知る限り)
- このクラウドのコンテナは使い捨て。成果物はファイルで渡し、ローカルへの配置はユーザーが行う

## 検討した案
| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| 1(採用) | 本文を1つ作り、ローカルとクラウドの2か所に置く | 公式の方法で単純 | 直すたびに2か所を更新する |
| 2 | 自分用のプラグインにする | 1か所の更新で済む見込み | 作る手間が大きい。自前配布でクラウドに同期されるか未確認 |
| 3 | リポジトリごとの CLAUDE.md(テンプレート) | 共同作業者とも共有できる | 既存リポジトリに反映されない |

案1を選んだ理由: 最小の手間ですべての環境に効く。二重管理が負担になったら案2に移る。

## ユーザーが決めたこと
- ルールの中身(14項目)
- 「デプロイ」は dev → main にマージする直前。dev 上でリファクタリング → セキュリティチェック → e2e → main の順
- e2e は GitHub Actions かユーザーの Mac で実行し、クラウドのコンテナ内では完結させない(私の解釈。訂正はなかった)
- feat ブランチへのコミットも、テストが通っていなければ行わない(追加の要望)
  - 私の解釈: ここでの「テスト」は単体・結合テストを指す。e2e 必須は main / dev へのマージのまま
  - テストファーストとは両立する。「テストを書く → 失敗を確認 → 実装 → 全テストが通る → コミット」の順にし、失敗している状態はコミットしない
  - テストを書いたら実行し、失敗したときの出力を計画書(`docs/plans/...`)の進捗欄に貼る。これで「先に失敗していた」ことが記録に残る
  - 実装中に既存のテストを緩めない。テストを変える必要が出たら手を止め、理由をユーザーに伝えて承認を得る
  - テストだけを先にコミットする方式(B案)は採らなかった。テストが甘く書き換えられたかを見抜く力は落ちるが、ブランチを常にテストが通る状態に保つことを優先した
  - 強制のしかた: まずは CLAUDE.md の文章で指示する。コミットは手元で行う操作なので GitHub 側の設定では止められず、確実に止めるには各リポジトリに git の pre-commit フックが必要になる。これは非ゴール(守られない項目が出てから強制を考える)に従って、今回は入れない

## 私が決めたこと(確認をお願いします)
1. **適用範囲**: コードを変える作業に適用する。質問への回答や調べものだけのときは、計画の合意などの手順を省く
2. **文書の置き場所**(各リポジトリ内):
   - `docs/plans/YYYY-MM-DD-<テーマ>.md`: 目的の大・中・小、調べた先行事例と出典、計画、進捗チェックリスト
   - `docs/log.md`: 判断の根拠、失敗、試行錯誤(追記していく)
   - `docs/status.html`: 全体像・進捗・課題の図(1ファイルを更新し続ける)
   - superpowers の `docs/superpowers/...` は使わず、上の場所に揃える。superpowers 自身も、置き場所はユーザーの指定を優先すると書いている
3. **確認用の動画や音声**: 容量が大きいので git には入れず(.gitignore)、ファイルとして直接送る
4. **main / dev へのマージ**: Claude の判断では行わず、ユーザーの承認を得てから
5. **ブランチ保護が使えないリポジトリ**: そのことをユーザーに伝える。そのうえで「e2e が通っていなければ Claude はマージしない」という運用ルールで補う
6. **本文の置き方**: `~/.claude/CLAUDE.md` の1ファイルにまとめる。`rules/` に分けると、クラウドに書き出すファイルが増えるため
7. **クラウドの適用先**: 今の環境「デフォルトクラウド環境」に設定する。もう一つの「Default」環境は、私のツールからは編集できない

## 変更(最終チェック後の見直し)
最終チェック(Important 3件)とユーザーの追加要望を受けて、次のように変更する。

**ユーザーが決めたこと**
- 適用するのは自分のリポジトリだけ
- 目的の整理・先行事例の調査・計画書・合意の手順は、リポジトリの方針や実装計画を決めるときに使う。誤字修正のような小さな作業には使わない
- リファクタリングは月1回程度にする。デプロイのたびには行わない
- 定期実行のセッションでは、承認を自動にする

**私の案(確認待ち)**
- 「自分のリポジトリ」の判定: リモートの所有者が、ユーザーの GitHub アカウントであるリポジトリ。リモートがないリポジトリも含む(GitHub のユーザー名は後で確認する)
- 適用の範囲: ルール全体を自分のリポジトリだけに適用する。他のリポジトリでは、そのリポジトリの方針に従う
- 計画の手順以外の節(テストとコミット、ブランチと e2e、動作確認、記録)は、自分のリポジトリでの変更すべてに適用する
- リファクタリングの頻度
  - デプロイの時点で、`docs/log.md` に記録した前回のリファクタリングから1か月以上たっていれば、デプロイの前に行う
  - 作業は `feat/refactor-YYYY-MM` で行い、PR で dev に入れる。dev へのマージ時に e2e を通す
  - これで、最終チェック Important-1 の食い違い(dev に直接コミットできない)も解消する
- デプロイの時点の手順: セキュリティチェック → 直すものがあれば feat で直して PR で dev へ → 単体・結合テストと e2e が通る → 承認を得て dev → main
- 定期実行
  - 指示文の先頭に `[定期実行]` と書いたときだけ、計画の合意と dev / main へのマージの承認を自動にする
  - テスト・e2e・セキュリティチェックが通らないときは、先に進まず止めて報告する
  - テストを緩める必要が出たときも、緩めずに止めて報告する
  - 自動で決めたことは、`docs/log.md` と最後の報告に残す

**ユーザーが決めたこと(同期)**
- 案A: 公開リポジトリを本文の正本にし、クラウドもローカルもそこから取り込む

**同期の設計(私の案)**
- リポジトリ: `NaoyaTAKIMOTO/claude-rules`(公開)。中身は次のとおり
  - `CLAUDE.md`(本文)
  - `check.sh`
  - `.github/workflows/check.yml`(push と PR のたびに check.sh を実行)
  - `README.md`(Mac での設定手順)
- このリポジトリ自体は、ブランチと e2e の決まりの対象外にする
  - 配信元は main なので、check.sh が通ったら main に直接入れる。テストが通ってからコミットする決まりは守る
- クラウドのセットアップスクリプト
  - 起動時に `https://raw.githubusercontent.com/NaoyaTAKIMOTO/claude-rules/main/CLAUDE.md` を取得する
  - 成功したら、そのまま `~/.claude/CLAUDE.md` にする
  - 失敗したら、「共通ルールの取得に失敗したので、ユーザーに伝える」という短い CLAUDE.md を書く。どちらの場合も終了コードは 0 にし、セッションの起動を止めない
  - 前に話した「今の本文を予備として埋め込む」案は採らない。予備は古くなるうえ、2か所のずれをなくすという同期の目的に反するため
- Mac
  - `~/claude-rules` にリポジトリを複製する
  - `~/.claude/CLAUDE.md` の末尾に `@~/claude-rules/CLAUDE.md` の1行を足して取り込む(公式の import 機能)。既存の内容は消さない
  - `~/.claude/settings.json` の SessionStart フックで `git -C ~/claude-rules pull --ff-only -q` を実行する。変更は次のセッションから効く
- 「自分のリポジトリ」の判定: リモートの所有者が NaoyaTAKIMOTO であるリポジトリと、リモートがないリポジトリ。他人のリポジトリのフォークは除く(元のリポジトリの決まりとぶつかるため)
- 制約: このセッションの GitHub トークンは無効で、リポジトリを新しく作れない。空の公開リポジトリはユーザーに作ってもらい、そこに push する

## 進め方と完了条件
1. ルール本文(CLAUDE.md)を作り、ユーザーに確認してもらう
2. 「デフォルトクラウド環境」にセットアップスクリプトを設定する(承認カードで確認)
3. 新しいクラウドセッションを1つ立て、ルールが読み込まれていることを確かめる
4. ローカルに置くためのファイルとコマンドを渡す
